DUCK HUNT MECHANICS IMPLEMENTATION SPEC FOR CURSOR
Plaintext engineering brief

Scope

Build a deterministic gameplay-mechanics recreation of NES Duck Hunt with these modes only:

1. GAME_A_ONE_DUCK: one duck at a time, single player only.
2. GAME_B_TWO_DUCKS: two ducks per wave, single player only.
3. GAME_C_CLAY_SHOOTING: two clay pigeons per wave, single player only.

Do not implement the hidden second-player duck-control behavior. Ignore controller-based duck steering entirely. This spec is for target behavior, shooting rules, round progression, scoring hooks, and timing. It does not include original art, original audio, title-screen behavior, pause behavior, or top-score persistence.

Use a fixed 60 fps gameplay update. Use a 256 x 240 NES virtual coordinate space, then scale to your display resolution. Keep entity positions as integer NES pixels unless a section says fixed point.

Source basis

- Duck Hunt disassembly, Duck-ssembly-Hunt, RussianManSMWC.
- Duck Hunt NES instruction booklet.
- NESdev Zapper behavior notes.
- Empirical flight analysis by GG for sanity checking speed, duration, and hitbox changes.

Implementation priority

To make the game feel like Duck Hunt, do these exactly:

1. Use a 60 fps fixed-step update.
2. Use motion-code micro-patterns, not smooth random velocities.
3. Use the speed-cycle table to apply 1 to 7 movement substeps per frame.
4. Use scripted paths for GAME_B_TWO_DUCKS.
5. Use launch paths plus boundary-driven random redirection for GAME_A_ONE_DUCK.
6. Use 3 shots per duck or pair.
7. Use 10 targets per round.
8. Use the pass-line table exactly.
9. Shrink the Zapper hitbox by round.
10. For clay pigeons, use the fixed-point projectile update and distance-based hitbox shrink.

------------------------------------------------------------
2. RNG MODEL
------------------------------------------------------------

The original uses a 4-byte shift-register RNG. For gameplay matching, implement this for explicit RNG calls used in path selection, release delay, color selection, and boundary direction changes.

Pseudocode

function rngNext():
    feedback = ((rngState[0] & 0x02) ^ (rngState[1] & 0x02)) != 0
    carry = feedback ? 1 : 0

    for i in 0..3:
        old = rngState[i]
        rngState[i] = ((carry << 7) | (old >> 1)) & 0xFF
        carry = old & 0x01

    return rngState[0]

Seed

If your seed byte is 0, initialize rngState[0] to 0x5F. For a modern deterministic clone, expose a seed option. The original also advances RNG while waiting for NMI, so exact emulator-level RNG timing depends on CPU timing. For a gameplay clone, call rngNext only at the explicit places described below.

------------------------------------------------------------
3. ZAPPER AND HIT DETECTION MODEL
------------------------------------------------------------

Modern input replacement

Use the mouse, pointer, or reticle position as the Zapper aim point. Convert the aim point to NES virtual coordinates.

When the player fires:

1. If shotCount == 0, ignore the shot.
2. Decrement shotCount immediately.
3. Test active shootable targets in target slot order.
4. If a target is hit, set it to its HIT state, increment currentHitCount, increment currentWaveHitCount, and stop testing further targets for that shot.
5. If nothing is hit and shotCount reaches 0, ducks enter fly-away behavior. Clays keep flying until their trajectory ends.

Original CRT behavior

The original flashes white 8 x 8 sprite squares over a target on a black screen. For a modern clone, simulate the union of those white 8 x 8 squares.

Hit test function

function pointHitsZapperShape(pointX, pointY, targetX, targetY, shapeId):
    for each (dy, dx) in ZAPPER_SHAPES[shapeId]:
        rectX = targetX + signed(dx)
        rectY = targetY + signed(dy)
        if pointX >= rectX and pointX < rectX + 8 and
           pointY >= rectY and pointY < rectY + 8:
            return true
    return false

Important: these offset pairs are listed as dy, dx. The first value modifies Y, the second modifies X.

5. DUCK MOTION MICRO-PATTERNS
------------------------------------------------------------

Do not use smooth velocities. Each motion code is a repeating list of tiny signed pixel deltas. Each movement substep consumes one delta pair. If the pattern reaches the terminator, loop to the beginning of that pattern.

Each pair is dy, dx.

Notes

- Codes 0-15 are the normal compass-like duck flight directions.
- Code 16 is used for falling wobble.
- Codes 18-20 are fast upward escape motions.
- Pattern entries of (0,0) are real no-op substeps in some patterns, not terminators. The terminator is only in the original data table. In this high-level representation, just loop the list.

6. SPEED CYCLE TABLE
------------------------------------------------------------

A speed index points into a 4-entry cycle. Each frame, read one value from the cycle. That value is the number of motion substeps to apply this frame. Then advance within the 4-entry group. When the index reaches the end of the group, wrap back to the start of that same 4-entry group.

SPEED_CYCLES_BY_INDEX = {
  0x00: [1,1,1,1],
  0x04: [2,1,1,1],
  0x08: [2,1,2,1],
  0x0C: [2,2,2,1],
  0x10: [2,2,2,2],
  0x14: [3,2,3,2],
  0x18: [3,3,3,3],
  0x1C: [4,3,4,3],
  0x20: [4,4,4,4],
  0x24: [5,5,5,5],
  0x28: [6,6,6,6],
  0x2C: [7,7,7,7]
}

Implementation

function readSpeedAndAdvance(entity):
    cycleStart = entity.speedIndex & 0xFC
    cycleOffset = entity.speedIndex & 0x03
    steps = SPEED_TABLE[cycleStart + cycleOffset]
    cycleOffset = (cycleOffset + 1) & 3
    entity.speedIndex = cycleStart + cycleOffset
    return steps

8. GAME A, ONE DUCK, SINGLE PLAYER ONLY
------------------------------------------------------------

Wave structure

- One duck per wave.
- Three shots per duck.
- No second-player duck control.
- The dog presentation can be simplified, but the duck launch timing should still start with releaseDelayFrames = 0x30 after the dog/wave handoff.

Game A duck speed by round

round 1:      speedIndex = 0x10, average 2.00 substeps/frame
rounds 2-3:  speedIndex = 0x14, average 2.50 substeps/frame
rounds 4-5:  speedIndex = 0x18, average 3.00 substeps/frame
rounds 6-7:  speedIndex = 0x1C, average 3.50 substeps/frame
rounds 8-9:  speedIndex = 0x20, average 4.00 substeps/frame
rounds 10-11:speedIndex = 0x24, average 5.00 substeps/frame
rounds 12+:  speedIndex = 0x28, average 6.00 substeps/frame

Game A fly-away timer

The timer starts only after the launch phase ends, meaning after the duck rises above the grass and y < 0x88.

Rounds 1-10:  timer = 0x7D ticks. Decrements every other frame. About 4.17 seconds after launch ends.
Rounds 11-19: timer = 0x5D ticks. Decrements every other frame. About 3.10 seconds after launch ends.
Rounds 20+:   timer = 0x3E ticks. Decrements every other frame. About 2.07 seconds after launch ends.

This is not the full visible lifetime. Full visible lifetime includes launch travel plus escape travel. Empirical sanity target: around 11.5 seconds visible on round 1, falling to about 5.1 seconds by round 20+.

Game A launch paths

Path IDs 0x10-0x1F are used. Each entry is:

[startX, launchSegmentDuration, initialMotionCode]

launchSegmentDuration is always 0xE0 substeps. The launch phase ends early when y < 0x88.

Game A state READY_WAITING_TO_LAUNCH

When releaseDelayFrames reaches zero:

1. Select launch path as above.
2. x = path.startX
3. y = 0xA8
4. motionCode = path.initialMotionCode
5. segmentTimer = path.launchSegmentDuration
6. pathIndex can point after the segment, but it will not matter after launchFlag clears.
7. launchFlag = true
8. flyAwayFlag = false
9. flyAwayTimer = selected by round
10. zapperShape = selected by round
11. speedIndex = selected by round
12. state = FLYING_AND_SHOOTABLE
13. currentTargetCount += 1

Game A active flying update

function updateGameADuck(duck):
    if shotCount == 0 and not duck.flyAwayFlag:
        duck.flyAwayFlag = true
        duck.segmentTimer = 0xF0
        setMotionCode(duck, 0)      // upward

    if duck.launchFlag:
        if duck.y < 0x88:
            duck.launchFlag = false
        else:
            applyScriptedLaunchMotionThisFrame(duck)
            return

    if not duck.flyAwayFlag:
        if frameCounter is odd:
            duck.flyAwayTimer -= 1
            if duck.flyAwayTimer == 0:
                duck.flyAwayFlag = true
                showFlyAwayMessageIfNoDuckHitThisWave()

    if duck.flyAwayFlag:
        updateDuckEscapeBoundaryLogic(duck)
    else:
        updateDuckNormalBoundaryLogic(duck)

    steps = readSpeedAndAdvance(duck)
    repeat steps times:
        applyNextMotionMicroDelta(duck)

    updateDuckAnimationFromMotion(duck)

Normal free-flight bounds

If not in fly-away mode, keep ducks in this box:

y < 0x20:  nudge y += 1 and choose a new downward-safe direction
y >= 0x90: nudge y -= 1 and choose a new upward-safe direction
x < 0x10:  nudge x += 1 and choose a new right-safe direction
x >= 0xF0: nudge x -= 1 and choose a new left-safe direction

After any boundary change, continue moving with the new motion code.

Escape bounds

When flyAwayFlag is true, use escape bounds instead of normal bounds:

if y < 0x08: clear duck
if x < 0x0C: clear duck
if x >= 0xF4: clear duck
if y >= 0x90: nudge upward and choose an upward-safe direction
otherwise continue movement and allow the duck to leave through the top or sides

Boundary direction selection

For a close recreation, implement this instead of simple vector reflection.

function chooseBoundaryMotion(duck, boundaryType):
    // boundaryType can be TOP, BOTTOM, LEFT, RIGHT.
    // This mirrors the original's biased redirection logic.

    if boundaryType == TOP:
        duck.y += 1
        boundaryCode = 0
        sideBase = duck.motionCode & 0x08
    else if boundaryType == BOTTOM:
        duck.y -= 1
        boundaryCode = 2
        sideBase = duck.motionCode & 0x08
    else if boundaryType == LEFT:
        duck.x += 1
        boundaryCode = 4
        sideBase = 0
    else if boundaryType == RIGHT:
        duck.x -= 1
        boundaryCode = 2
        sideBase = 0x08

    base = ((duck.motionCode & 0x07) ^ 0x07) | sideBase
    r = rngNext() & 0x03
    if r == 3: r = 2
    candidate = base + r

    if candidate == 0:
        if boundaryCode == 2: candidate -= 1
        else: candidate += 1
    else if candidate == 4:
        if boundaryCode == 0: candidate += 1
        else if boundaryCode == 2: candidate -= 1
        else: candidate += randomPlusMinusOne()
    else if candidate == 8:
        if boundaryCode == 0: candidate += randomPlusMinusOne()
        else: candidate -= 1
    else if candidate == 12:
        if boundaryCode == 0: candidate -= 1
        else: candidate += 1

    duck.motionCode = candidate & 0x0F

function randomPlusMinusOne():
    // Original uses bit 7 of rngNext after an ASL.
    return ((rngNext() & 0x80) != 0) ? +1 : -1

Hit and fall behavior

When hit:

1. state = HIT_MARK_AND_SCORE.
2. Mark hit table for this target.
3. currentHitCount += 1.
4. currentWaveHitCount += 1.
5. Add score according to color and round.
6. Enter HIT_PAUSE for 0x12 frames.
7. Then enter START_FALLING.
8. In falling, use motion code 16 and fall until y >= 0xB0.
9. Then clear the duck.

- Two duck slots are enabled.
- Three shots are shared by both ducks.
- First duck launches after releaseDelayFrames = 0x30 frames.
- Second duck launches after a random delay of 1 to 64 frames after the first duck initializes.

Game B path format

Each path is:

[startX, duration1, motionCode1, duration2, motionCode2, ..., 0xFF, nextState, extra]

Duration is in movement substeps, not frames. Higher speed cycles consume the same path faster because more substeps are applied per frame.

When segmentTimer reaches 0:

1. Read the next byte.
2. If it is 0xFF, set state = nextState and stop.
3. Otherwise, that byte is segmentTimer.
4. Read the following byte as motionCode.
5. Continue movement.

function spawnDuckWave():
    shotCount = 3
    currentWaveHitCount = 0
    releaseDelayFrames = 0x30

    select currentDuckConfiguration as described above

    duckSlot0.active = true
    duckSlot0.state = INIT

    if mode == GAME_B_TWO_DUCKS:
        duckSlot1.active = true
        duckSlot1.state = INIT
        pendingDuckLaunches = 2
    else:
        duckSlot1.active = false
        duckSlot1.state = IDLE_OR_CLEARED
        pendingDuckLaunches = 1

function updateDuckModeFrame():
    handleShotInputIfAny()

    updateDuck(duckSlot0)
    updateDuck(duckSlot1)

    if pendingDuckLaunches > 0 and releaseDelayFrames > 0:
        releaseDelayFrames -= 1

    if pendingDuckLaunches == 0 and no duck slot is active or shootable:
        showDogResultOrRoundEnd()

function updateDuck(duck):
    switch duck.state:
        case IDLE_OR_CLEARED:
            return

        case INIT:
            initializeDuckDefaults(duck)
            duck.state = READY_WAITING_TO_LAUNCH
            return

        case READY_WAITING_TO_LAUNCH:
            if releaseDelayFrames > 0: return
            initializeDuckLaunch(duck)
            pendingDuckLaunches -= 1
            releaseDelayFrames = (rngNext() & 0x3F) + 1
            return

        case FLYING_AND_SHOOTABLE:
            if mode == GAME_A_ONE_DUCK:
                updateGameADuck(duck)
            else:
                updateGameBDuck(duck)
            return

        case HIT_MARK_AND_SCORE:
            markHitAndAddScore(duck)
            duck.hitPauseTimer = 0x12
            duck.state = HIT_PAUSE
            return

        case HIT_PAUSE:
            duck.hitPauseTimer -= 1
            if duck.hitPauseTimer == 0:
                duck.state = START_FALLING
            return

        case START_FALLING:
            spawnScorePopup(duck)
            setMotionCode(duck, 16)
            duck.state = FALLING
            return

        case FALLING:
            steps = readSpeedAndAdvance(duck)
            repeat steps times:
                applyNextMotionMicroDelta(duck)
            if duck.y >= 0xB0:
                duck.state = CLEAR
            return

        case CLEAR:
            clearDuckSprites(duck)
            duck.active = false
            duck.state = IDLE_OR_CLEARED
            return

function updateGameBDuck(duck):
    if shotCount == 0 and not duck.flyAwayFlag:
        duck.flyAwayFlag = true
        duck.segmentTimer = 0xF0
        setMotionCode(duck, 0)

    if duck.segmentTimer == 0:
        byte = duck.pathData[duck.pathIndex]
        duck.pathIndex += 1

        if byte == 0xFF:
            duck.state = duck.pathData[duck.pathIndex]
            duck.pathIndex += 1
            duck.extra = duck.pathData[duck.pathIndex]
            return

        duck.segmentTimer = byte
        newMotion = duck.pathData[duck.pathIndex]
        duck.pathIndex += 1
        setMotionCode(duck, newMotion)

    steps = readSpeedAndAdvance(duck)
    repeat steps times:
        if duck.segmentTimer > 0:
            duck.segmentTimer -= 1
        applyNextMotionMicroDelta(duck)

    updateDuckAnimationFromMotion(duck)

11. GAME C, CLAY SHOOTING, SINGLE PLAYER ONLY
------------------------------------------------------------

Wave structure

- Two clay slots are enabled.
- Three shots are shared by both clays.
- At the start of each pair, releaseDelayFrames = 0x80.
- First clay launches when releaseDelayFrames reaches zero.
- Second clay launches after a random delay of 1 to 64 frames after the first clay initializes.
- No dog target behavior is needed for clay mode.

ClayState

0 IDLE_OR_CLEARED
1 INIT
2 READY_WAITING_TO_LAUNCH
3 FLYING_AND_SHOOTABLE
4 HIT_START_FRAGMENTATION
5 FRAGMENTING
8 CLEAR

Clay trajectory model

The original clay pigeon uses three 5-byte fixed-point groups. Treat these as internal projectile values, not screen pixels. The screen x and y are projected from these values each frame.

Use entity memory bytes m[0..14] representing original addresses $40..$4E:

Group A, m[0..4], original $40..$44: horizontal-ish component.
Group B, m[5..9], original $45..$49: distance/depth component.
Group C, m[10..14], original $4A..$4E: vertical-ish component.

Each group layout:

m[base + 0] = acceleration
m[base + 1] = velocity low
m[base + 2] = velocity high
m[base + 3] = position low
m[base + 4] = position high

Clay path table

Each launch path has 6 bytes:

[set_$44, set_$43, set_$4A, set_$42, set_$47, set_$4C]

Clay fixed-point update

Use unsigned 8-bit math. Values wrap at 0xFF. Signed checks use bit 7.

function signByte(b):
    return 0xFF if (b & 0x80) else 0x00

function updateClayFixedPoint(m):
    // Update groups in this order: group C at base 10, group B at base 5, group A at base 0.
    for base in [10, 5, 0]:
        acc = m[base + 0]
        signAcc = signByte(acc)

        // velocity low += acceleration
        sum1 = acc + m[base + 1]
        carry1 = sum1 > 0xFF ? 1 : 0
        m[base + 1] = sum1 & 0xFF

        // velocity high += sign(acceleration) + carry
        sum2 = signAcc + m[base + 2] + carry1
        m[base + 2] = sum2 & 0xFF
        signVelHigh = signByte(m[base + 2])

        // Original doubles velocity low and uses its carry while adding velocity high to position low.
        carryFromVelLowShift = (m[base + 1] & 0x80) ? 1 : 0
        m[base + 1] = (m[base + 1] << 1) & 0xFF

        // position low += velocity high + carryFromVelLowShift
        sum3 = m[base + 2] + m[base + 3] + carryFromVelLowShift
        carry3 = sum3 > 0xFF ? 1 : 0
        m[base + 3] = sum3 & 0xFF

        // position high += sign(velocity high) + carry
        sum4 = signVelHigh + m[base + 4] + carry3
        m[base + 4] = sum4 & 0xFF

function updateClay(clay):

Clay projection

For a close clone, port the original projection routine. For a gameplay-feel clone, use this approximation:

z = max(1, clay.m[9])
rawX = ((clay.m[4] << 8) | clay.m[3])
rawY = ((clay.m[14] << 8) | clay.m[13])

screenX = 128 + ((signed16(rawX) * 108) / (z + 32))
screenY = 176 - ((signed16(rawY) * 80) / (z + 32))

Clamp only for rendering. Do not clamp the internal fixed-point trajectory. The original clears the target when m[14] is negative or m[9] >= 0x30.

function handleShotInDuckMode(pointX, pointY):

------------------------------------------------------------
13. ACCEPTANCE CHECKS
------------------------------------------------------------

Use these to check whether your implementation is close.

General

- Round always contains 10 targets.
- Game A has 1 duck per wave and 3 shots per duck.
- Game B has 2 ducks per wave and 3 shots total for the pair.
- Game C has 2 clays per wave and 3 shots total for the pair.
- The pass line is 6 hits through round 10, then 7, 8, 9, and finally 10 from round 20 onward.

Game A

- Round 1 ducks should feel slow and stay visible a long time, around 11.5 seconds total on average including launch and escape travel.
- Around round 8, average speed should feel roughly double round 1.
- Around round 12, average speed should feel roughly triple round 1.
- Around round 20, ducks should be visible roughly 5 seconds on average.
- Hitbox remains large through round 23, shrinks at round 24, then shrinks again from round 27 onward.
- Do not steer with controller input. This implementation is single player only.

Game B

- Two ducks launch with a stagger. First after about 48 frames, second after a random 1 to 64 frame delay.
- Ducks follow scripted paths, not bouncing free-flight behavior.
- Path completion speeds up because speed cycles consume more path substeps per frame.

Game C

- Two clays launch with a stagger. Pair start delay is about 128 frames, then second clay uses a random 1 to 64 frame delay.
- Clays shrink quickly as they move away.
- Clays are easier to hit when close because they use larger Zapper shapes, then shrink by distance and round bracket.
- Round 10+ clays should stay visible about 2.8 to 3.3 seconds depending on path.

------------------------------------------------------------
14. THINGS TO AVOID
------------------------------------------------------------

Do not implement ducks as physics bodies with random acceleration.
Do not use one smooth velocity vector per duck.
Do not give Game A and Game B the same flight behavior.
Do not implement second-player controller duck movement.
Do not make hitboxes equal to the visible sprite bounds.
Do not forget that Game B and Game C use 3 shots total for two targets.
Do not make the pass line increase every round. It uses the fixed table above.
Do not clamp clays visually by screen bounds. They clear by internal distance or vertical fixed-point state.
